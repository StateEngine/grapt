# Grapt agent guide

Grapt is a coding-agent harness: runtime, server, TUI and CLI, written in Rust.
It must work for a stranger on their first try, on a clean machine, with no manual steps.
Release criteria live in `docs/RELEASE-0.1.md`. Nothing else gates a release, and work
that closes no open criterion waits.

## This repository is going public

Write everything as if it were already public: code, tests, fixtures, comments, docs and
commit messages.

- Never include secrets or tokens, even expired ones.
- Never include personal names or emails, except in required license notices.
- Never include machine or fleet details: hostnames, non-loopback IPs, real home or drive
  paths, agent names and ids, internal message or ticket ids.
- Tests use neutral placeholders and temp directories, and synthetic credentials that are
  obviously fake. Never use or link a real account's credential file in a test.
- Keep diagnostics, evidence and reports out of the repo.
- Product code carries no operator defaults: no fixed agent names, hosts or drive paths.
- Don't change license text. The project's copyright holder is "The Grapt Authors" (the
  operator's 2026-11-18 ruling). Add required upstream licenses and notices unchanged.
- Check your diff and message for all of this before you commit. If something slipped
  through, fix it in a new commit and tell the reviewer.
- Never force-push or rewrite shared history.

## Other products

Never describe our work in terms of another tool: no "like X", "matching X", "as X does",
"adapted from X" or "copied from X" in commits, PR text, code, comments or docs. Describe what
our code does on its own terms. Naming providers we connect to, dependencies we use and
required license notices under `notices/` is fine; provenance of reused code lives only there.

## Commits

- Subject: `type(scope): imperative summary`, under 72 characters.
- Body: optional, at most two short lines, and only the why the diff can't show. The
  trailer line doesn't count against that limit.
- Author: a GitHub noreply address, never a personal or machine email. Agents use the
  project's configured identity; check `git config user.email` before committing.
- Agent commits end with exactly one of these lines, naming the harness, not the model:
  - `Co-Authored-By: Claude <noreply@anthropic.com>`
  - `Co-Authored-By: Codex <noreply@openai.com>`
  - `Co-Authored-By: secode-seats <353560407+secode-seats[bot]@users.noreply.github.com>`

  GitHub credits co-authors by address, so any other name or address can credit a stranger.
- No test counts, gate results, evidence, status or reasoning about process. Recent commit
  messages are read into agent context, so every extra word is paid for again and again.
- PR text has three parts: Testing (how you checked it and what you could not check), Risk (its
  tier and why), How to revert. No test logs, evidence files, process notes or internal ids.

## Reuse before you build

Approved sources are listed in `notices/02-approved-sources.md`. Taking code from any other
open-source project needs the maintainer's approval first. Never copy from
proprietary software: for that, only describe its observable behaviour and write our own. Read how approved sources
solve a problem first, then adapt the code to our lint and architecture rules rather than
wrapping it. Check the LICENSE at the commit you copy from
and keep the Apache notice. Record each adaptation as one small fragment under `notices/`:
a table row in `notices/10-adoptions/` or a section in `notices/90-sections/`, with a
filename starting with a letter and a trailing newline. Never edit
`THIRD_PARTY_NOTICES.md`; it is generated by `python3 scripts/release/notices.py`.

## What must never be compromised

- **Honest results.** Absent, unreadable and zero are different facts. Never collapse them,
  discard a failure, truncate silently, or report success without a witness.
- **Other agents' work and users' data.** Anything that can eat either is a blocker, not a
  style point.
- **Refusals that help.** A refusal names its reason and a step that actually works. Don't paper
  over a product gap with instructions: users won't have our files, so the cure belongs in source.

## Implementation rules

- Keep IDs and lifecycle vocabularies as their owning newtypes, never raw strings.
- Keep synchronous domain and store ownership separate from async I/O. No SQLite
  transaction, mutex guard or aggregate borrow survives an await.
- Keep channels bounded and observable. Durable commit precedes live notification.
- Treat malformed fixtures, missing evidence and unavailable required inputs as failures.
- No broad lint suppressions, `unsafe`, unbounded streams, generic provider parameter maps
  or Effect-shaped layers. FFI goes through an exact-pinned crate that owns the unsafe.
- No `unwrap` or `expect`, including in tests. The clock and randomness methods listed in
  `clippy.toml` are banned except at named adapter sites; Tokio scheduling is allowed.
  `DiagnosticClock::new` in `crates/grapt-cli/src/acp/timing.rs` is a diagnostic-only
  exception: its readings never enter durable data, ordering or OAuth expiry.
- Intentional non-parity needs a scenario-local waiver.
- Give every module one responsibility and split code along responsibilities, never to beat a
  size limit (see Craft under Review). Keep a module's types and helpers with it. Never use
  `include!` to stitch Rust source into one scope; use a submodule with a real interface.
- Speed and memory are product features. Measure them; don't claim "fast" without numbers.
- Open real user databases read-only. Never write to one from this repo.
- Every landing must work on both Linux and Windows, and say what it did not exercise on
  macOS. Run Windows-target Clippy before review: Linux-target Clippy doesn't compile
  Windows-only code.
- A fix on one path is often missing on its twin. Check both: TUI and CLI, desktop and TUI,
  Windows and Linux, each provider, read and write. Say why if one side is exempt.

## Craft

- A plan names the crate and module for each new piece of code before coding it.
- Wrong placement is an Important review finding even below the file size limits.
- The affected and full gates print an advisory, never a failure, for each changed
  `crates/**.rs` file that ends over 700 physical lines. The hard structural laws
  are shrink-only: no new `include!()` in production `src/`, no new
  `reason = "legacy"` `#[expect]`, no new module cycles in lib or bin crates, and
  reviewed workspace edges in `crate-graph.json`.

## Working method

- When something that used to work breaks, find what changed first (`git log -S`, recent
  landings). Name the change, or show history is silent, before redesigning.
- A question gets an answer, not an edit. Propose simplifications before building.
- Prove behaviour through its real consumer, not only an isolated test. A truthful refusal
  isn't a supported outcome.
- Before blaming the base for a failure, reproduce it there. Use `--no-fail-fast` when
  attributing, because cargo otherwise stops at the first failing test binary.
- A change isn't live until the process using it restarts. Restart it, make the effect
  happen, and read it back from outside the writer.
- Don't add a new guard per incident when a smaller product fix removes the cause.
- Use your own judgment and finish the whole outcome before asking for review. Escalate only
  what needs missing access, breaks a stated constraint, or changes the agreed outcome.
- Don't poll long jobs, because each check costs tokens. Wait for their completion.

## Commands

```
cargo fmt -p <crate> --check      # never --all
cargo clippy -p <crate> --all-targets -- -D warnings
cargo test -p <crate>
```

Build heavy tests in your own target directory, one build at a time, and clear it when the
work has landed.

## Shared repository safety

Many worktrees share one `.git`.

- Never `git stash`: the stack is shared, so a pop can take someone else's work.
- Never `git commit --amend` in a shared tree. Use path-limited commits:
  `git commit -F - -- PATH1 PATH2`. Never `git add -A`.
- Start a slice only from an accepted commit, never from another unreviewed worktree.
- Author in your own worktree. Never link `node_modules` into one, and remove worktrees only
  with the supported tool: a recursive delete can follow a link into shared files.
- Stop processes only by exact pid, after reading the full command line. Never by name.
- Read exit codes directly, not through a pipe.
- On Windows, never rewrite source through PowerShell `Get-Content`/`Set-Content`: it can
  silently corrupt UTF-8.
- Preserve other contributors' uncommitted files. Commit only your own slice.

## Tests

- Authors should avoid writing tests. Reviewers write them as needed, especially when they
  find a bug: a good one fails on the base and passes on the fix.
- If an author does add one, keep it to a behaviour test at a public seam. Test lines never
  exceed product lines.
- No exact-layout, snapshot or frame-content assertions. No new witness, journey or bench
  scripts.
- Tests over about 60 seconds go in the nightly tier, tagged by exact name in
  `scripts/build/slow_tests.py`. Never shorten their workload or silently skip one.
- Author test results are a development aid, not evidence.
- A test that breaks on an unrelated change gets deleted or loosened, not re-pinned.
- Test doubles must behave like the real thing they replace.

## Review

Before asking for review, review your own diff in a fresh context and fix what you find.

Risk sets the review, and the change sets the risk, not the author:

| Risk | Examples | Review |
|---|---|---|
| Low | Docs, tests, copy | CI only |
| Medium | Ordinary product changes; a provider connection that only uses the existing credential store with an official SDK or approved source | One reviewer |
| High | Tier 1 below: credentials, sandbox, migrations, installers, data deletion | Two reviewers. Native Windows runs as a standard user happen on the release candidate |

- Report correctness and craft separately, and say what you did not exercise. Is it over- or
  under-built, in the right layer, easier to work in afterwards? Green with poor craft goes
  back.
- Craft includes structure, around the change and not just in the diff. Follow the single
  responsibility principle: each module has one reason to change, and code is split along
  responsibilities, never to beat a size limit. These are Important findings, not nits:
  - Rule gaming: obeying a rule's wording while defeating its purpose. That includes splitting
    a file just to pass a limit, a file pressed against the line cap, stitching code back with
    `include!`, silencing a check instead of fixing the cause, and weakening a test until it
    passes.
  - Boundary violations: reaching into another module's private state, several levels up with
    `super::super::`, past a crate's public interface, or around an existing check or safety step.
  - Coupling and length: a new cycle between modules, or a function too long to follow in one
    read.
- Limits are warning signs, not goals. When one trips, extract a distinct responsibility; don't
  slice the file in half.
- Some code is legitimately large: generated tables, a dispatcher or state machine that reads
  best in one place, protocol definitions, test fixtures. It gets a named exception with a
  one-line reason, approved in review: an `#[expect(..., reason = "...")]` on that item.
  A forced split that scatters one idea is as bad as a grab bag.
- Items that broke a limit before it existed carry `reason = "legacy"`. Don't grow them; the
  build fails once one is split back under the limit, so delete its marker then. Never add a
  new `legacy` marker.
- Tag every finding Important, Nit or Pre-existing, with file and line evidence and no
  guesses. Cap nits at three. Pre-existing findings don't block; they get their own change.
- Start with a count of findings, and say plainly when nothing needs fixing.
- Flag the class of bug, so the author fixes every instance. Don't repeat a posted finding.
- Every Important finding gets fixed or answered with a reason before landing.
- After the first review, re-review only the new diff. After three rounds, stop and reconsider
  the approach instead of adding another fix.
- The same goes for CI: after three failures in a row on your change, stop pushing. Read the
  failing log, reproduce the failure, and check whether `main` is red, then change the approach
  and tell the merger what you found before you push again.

## Landing

`main` is the canonical integration branch. Start short-lived author branches from an
accepted `main` commit, and target `main` in pull requests.

A slice needs the review its risk tier requires and its required gate.

- **Affected gate:** fmt and clippy `-D warnings` on touched crates, tests of those crates
  and their direct dependents (`grapt-tui` too if an HTTP route changed), and the four
  law checks (`no_god_files`, `direct_include_format`, `crate_graph`, `write_chokepoint`).
- **Full gate before landing:** changes to `grapt-types`, `grapt-store`, `grapt-runtime`,
  `grapt-event`, `grapt-schema`, build or gate tooling, release packaging, and package
  builds. The landing batch's full gate provides it.
- **Tier 1 keeps strict review and named failure tests:** schema and migrations, durable
  writes, permissions, credentials, sandbox, update and rollback, user-data deletion. Its
  Windows checks run as a standard user, not an administrator, on the release candidate.
- Docs-only changes don't get their own PR; include them with your next code change.
- One designated merger lands every change. After ACCEPT, hand over the exact commit and
  don't run `scripts/land.ps1` yourself. Follow any active landing order or hold.
- Pull request CI checks the affected crates only. The merger lands accepted pull requests
  together on a `batch/` branch; its gate qualifies them, then `main` fast-forwards to it.
  The batch gate is affected unless the batch touches core crates, build tooling or
  release paths, which keep it full; the nightly full gate covers `main`. Don't run your
  own full gate on code that is already in a pull request.
- One open pull request per seat: while yours is unmerged, work on its corrections,
  reviews or local drafts. No author test batteries on the box; reviewers build only
  their judging test. Heavy native or VM runs are for High-risk changes only.
- Push a pull request once it is ready for review, and push corrections together after the
  review. Every push restarts that pull request's CI.
- A rebase that leaves the slice's own diff unchanged keeps its ACCEPT; only the gate
  reruns.
- Run heavy jobs through the scheduler (`scripts/build/heavy.py`) with `--nvme` and a target
  on that disk. A job without it takes the whole host and holds everyone else back, so go
  exclusive only for a stated reason. Follow any active hold on gate entry points.
- Never start a native gate or heavy build on a live user or product machine. The scheduled
  build host and the governed hosted and VM routes are where they belong.
- Nightly runs the full gate. A red nightly is bisected, and the culprit's owner fixes it
  first. Keep `main` releasable.

## Working with other agents

Work without supervision. Send a message only for a slice ready for review, a verdict, a
blocker only someone else can clear, or a landing. No progress reports or acks. At most
five plain sentences, naming only the one commit that matters.

## What counts

User-visible changes landed, open release criteria, tool-failure rate and cache read share
per model. Commit counts, test counts, message counts and evidence volume are not progress.
